Architecture report — Restro App

How the restaurant management system actually works

A walkthrough of the real system: a JSON-document backend wearing a SQL-shaped identity layer, three roles with sharply different blast radii, and a delivery-payments flow built to survive duplicate names and half-typed filters. Written from the current code, not the docs.

01 Overview

Node/Express API, React SPA, same app also ships as an Electron desktop build. One restaurant per tenant, tenants isolated by restaurantId on almost every record, plus a separate Super Admin layer that sits above all restaurants.

React SPA (Vite)→ Express API→ repo(collection)→ Postgres JSON store or local files (offline)

The same frontend build runs online against Supabase/Postgres and offline against local JSON — the switch is PERSISTENCE_MODE, invisible to the UI.

02 Storage model

Two different storage strategies coexist on purpose, split by how structured the data needs to be.

Real tables

Only identity/session data gets actual Postgres DDL, because it needs constraints and cross-tenant lookups: restaurants, users, super_admins, licenses, devices, login_sessions.

JSON documents

Every business entity is a row in one generic records(collection, id, data) table, validated against a hand-written schema — orders, clients, products, cashierShifts, deliveryAgents, cashLedger, and 16 more.

"Adding a field" to an order means adding a key to its schema entry in backend/src/models/index.js — not a migration. Old records simply lack the key until they're next written. All access goes through repo(collection), which picks the Postgres-backed or local-JSON-backed repository transparently and applies a 2.5s read cache per collection (invalidated on every write) so dashboard/report pages don't fan out into dozens of reads per request.

03 Identity & roles

Three roles, one hard boundary between them: SUPER_ADMIN operates across restaurants, ADMIN and CASHIER are both scoped to exactly one.

SUPER_ADMIN

Creates restaurants, issues licenses, manages every restaurant's users, can suspend/delete/reset-password. Bypasses every rbac() check by design.

ADMIN

Full control within one restaurant — products, workers, reports, settings, finance. Gated by rbac('ADMIN') on admin-only routes.

CASHIER

Operational parity with ADMIN on POS-adjacent work (orders, clients, pending payments, cash drawer) — deliberately, so a shift can run without an admin present. Locked out of workers/reports/settings.

Every request carries a JWT with { sub, restaurantId, role }. createCrudService() — the factory almost every service is built on — enforces the restaurantId check on get/update/remove itself, so tenant isolation isn't something each route has to remember to do.

Same username, different restaurants is explicitly supported: the Postgres unique constraint is scoped to (restaurant_id, username), and login disambiguates same-username accounts using a device-fingerprint → restaurantId hint before falling back to password matching.

04 Licensing & devices

Every restaurant runs against a license record, checked at login and re-validated on a schedule — including while fully offline.

expirationDateHard stop — license simply expires.
validationIntervalHoursHow often a device must phone home online before its offline lease goes stale.
offlineDaysHow long a device may keep operating with zero connectivity before it's locked out.
maximumDevicesDevice cap per restaurant, enforced at activation.
sessionTimeoutMinutesIdle-session cutoff, swept server-side by a background job.

Offline operation works via an ECDSA-signed "offline license" issued at login/activation and re-verified locally by the Electron/browser client — the server doesn't need to be reachable for the app to keep enforcing its own expiry.

05 POS & orders

The order is the spine of the app — almost every other module (loyalty, cash drawer, reports, pending payments) is a view or a side effect of orders being created.

An order carries its own lifecycle status (pending → preparing → completed, or cancelled) completely independently from payment. That separation is what makes delivery payments possible without corrupting kitchen/order-tracking logic.

06 Delivery payments

The part of the app with the most deliberate design: an order can be handed to a courier before the cash is collected, and the system has to track that gap correctly across restaurant-scoped, duplicate-name-tolerant delivery agents.

Four payment scenarios

Paid nowPrinted immediatelypaid+1 immediatelyNever

The single field that drives all of this is paymentTiming (PAID_NOW | END_OF_DAY | UNPAID_PRINTED) — it decides whether paymentStatus is ever non-null, and the Pending Payments query is just rows.filter(o => !!o.paymentTiming).

Why deliveryAgentId, not the name

Delivery agents are their own restaurant-scoped collection with a stable id; orders store deliveryAgentId and snapshot deliveryAgentName for display only. Every filter, settlement, and total is keyed off the id — verified with a regression test using two agents deliberately both named "Ahmed," where filtering by each one's own id returns only that agent's orders.

Filters compose with AND, not OR

Agent, date range, status, and search are sequential .filter() calls on the backend — inherently AND. dateTo is bumped by 23:59:59.999 so a date-only string like "2026-07-24" (which parses as UTC midnight) still includes orders placed that entire day.

Two UI bugs fixed this cycle, not logic bugs. The filter row had overflow-x: auto for horizontal scroll — CSS spec forces overflow-y to auto too in that case, which silently clipped the Delivery Agent/Status dropdown popups shut. And the search box fired a request per keystroke with no response-sequencing, so a slow, stale response could overwrite a newer one. Both fixed without touching the filter logic itself, which was already correct.

07 Cash drawer & ledger

One append-only ledger is the source of truth for cash-on-hand; the drawer total shown in the UI is always read from it, never computed independently on the frontend.

  • Cash Ledger — record() appends an entry per cash-moving event (order paid, payment settled, order cancelled/reversed, cash advance); balance()/shiftContribution() read it back.
  • Settlement ("Collect") is wrapped in a per-order mutex (withLock) so it can't double-fire: paymentStatus → paid, paidAt stamped, exactly one ledger entry, no reprint.
  • Shared frontend state — a small Zustand store (usePosStats) holds the restaurant-wide drawer total and pending-payments count/total, refreshed once and shared by the POS badge, Dashboard, and Pending Payments summary tiles, so settling on one page updates every other mounted view instantly with no reload.

08 Back-of-house modules

Everything downstream of orders/cash follows the same shape: a service built on createCrudService, restaurant-scoped, CRUD routes, a matching page.

Inventory & goods

Workers & scheduling

Attendance, shifts, salaries, cash advances against pay.

Clients & loyalty

Customer records, location cascades (City → Area), loyalty points engine.

Reservations & complaints

Table booking and customer-complaint tracking.

Finance

Kitchen (KDS)

Kitchen display tickets generated from live orders.

09 Super Admin

A separate login (/superadmin/login), separate table (super_admins), separate dashboard — never reachable from a restaurant's own login.

  • Create restaurants, issue/adjust licenses (validation interval, offline days, device cap, session timeout).
  • Create/suspend/delete/reset-password on any restaurant's users — deletion is a soft status:'inactive', never a hard delete, so historical orders/salaries referencing that user stay intact.
  • Critical account changes (delete, suspend, password reset) revoke that user's active sessions, so an old JWT can't keep working after the account underneath it changed.

10 Frontend shape

React Router SPA, one Protected wrapper distinguishing "any logged-in role" routes from admin-only ones, shared UI primitives in one file.

  • components/ui.jsx — the entire design vocabulary: Card, DataTable, Dropdown, DateField, Stat, Badge, used identically across every page rather than each page rolling its own.
  • store/ — small Zustand stores: auth (session/license), ui (language, notifications, confirm dialogs), posStats (shared drawer/pending totals), connectivity (online/offline).
  • Route-level code splitting via lazy imports, with manual vendor chunks (React, Recharts, i18next) so they're cached once instead of duplicated per route.

11 i18n & offline

English/Arabic side by side, RTL handled at the layout level rather than per-component — direction flips, translations swap, no hardcoded left/right positioning to chase down.

Offline mode is a first-class path, not a fallback: PERSISTENCE_MODE=local swaps every repo() call to local JSON files with the same interface, a sync engine reconciles with Supabase (last-write-wins) once connectivity returns, and the offline license (above) keeps enforcing expiry the entire time.

12 Testing & conventions

Vitest on both sides; the backend suite runs against the same local-JSON path production offline mode uses, so tests exercise the real persistence code, not a mock.

Backend

Per-service test files beside their source (orderService.test.js, authService.concurrency.test.js, …) plus dedicated concurrency tests for the login/lock-sensitive paths.

Frontend

Page-level render/smoke tests plus targeted behavior tests (e.g. cash-drawer safety on the Orders page) under pages/__tests__.
